# Тёмный фэнтези-рендер карты — Подпроект 1: Растровая заливка и палитра

## Контекст

Сейчас `WorldMapRenderer` строит один меш из вееров треугольников на клетку и красит его через vertex color (`RegionColorPalette`) — результат читается как плоские цветные полигоны Вороного. Задача инициативы «Тёмный фэнтези-рендер карты» — заменить это на нарисованную от руки, тёмную и холодную картографию.

Источник дизайна: сессия в Claude Design, результат сохранён в `design_handoff_realmweaver_map/` (`README.md` — полная спецификация пайплайна/палитр/спрайтов/POI/тумана войны; `CLAUDE_CODE_UNITY.md` — инструкция интеграции в Unity; `Terra Umbrarum.dc.html` — рабочий референс, открывается в браузере; `screens/*.png` — скриншоты). Прототип независимо генерирует elevation/moisture/warmth через собственный per-pixel fbm-шум. **Мы не переиспользуем этот генератор** — вместо этого рендер-слой читает уже посчитанные поля существующих `VoronoiCell` (`EffectiveElevation`, `EffectiveTemperature`, `EffectiveMoisture`, `Biome`, `RegionId`, `EffectiveIsOcean/EffectiveIsLake`). JS-математику из хендоффа рассматриваем как точный псевдокод алгоритма шейдинга, не генерации.

Инициатива разбита на 6 независимых подпроектов (каждый опирается на предыдущий):
1. **Растровая заливка и палитра** (этот документ) — фундамент, всё остальное рисуется поверх.
2. Спрайты рельефа (горы/деревья/холмы/камыши/меса).
3. Реки (новый стиль рендера поверх уже готовой трассировки).
4. POI-маркеры (медальоны, расширение с 4 до 11 типов).
5. Подписи и рамка карты (компас/масштаб/картуш/виньетка).
6. Панель настроек палитры/твиков.

Туман войны (из хендоффа) вынесен отдельным пунктом в roadmap на будущее — в проекте пока нет концепции «партия/исследование», необходимой для его осмысленной реализации.

## Цели

- Заменить плоскую vertex-color заливку клеток на растровый (текстурный) рендер со сглаженными границами биомов, рельефным затенением, региональными вариациями тона, зерном, свечением берега и градиентом глубины воды.
- Ввести систему из 4 тёмных фэнтези-палитр (токены цветов) с активной по умолчанию «Холодный сумрак» (`ColdTwilight`).
- Сохранить точность существующей модели данных: биом не переклассифицируется заново (используем нашу 16-значную таблицу Уиттекера, она богаче упрощённых категорий прототипа), а мапится на визуальные семейства/слоты палитры.
- Не сломать существующее взаимодействие: кисть, выбор клетки, POI-размещение, undo — всё это зависит от точного попадания клика в конкретную клетку.
- Заодно закрыть застарелый пункт roadmap: `RecolorOnly()` сейчас перекрашивает весь меш на каждое движение кисти — новая архитектура даёт естественную возможность перекрашивать только задетую область.

## Не-цели (явно вне этого подпроекта)

- Спрайты гор/деревьев/холмов/камышей/меса — подпроект 2.
- Рендер рек в новом стиле — подпроект 3 (проследить/включить `enableRivers` здесь не пытаемся).
- Редизайн POI-маркеров (медальоны, 11 типов) — подпроект 4. Существующие плейсхолдеры (`PoiPlaceholderFactory`) не трогаем.
- Подписи регионов, компас, масштабная линейка, картуш, рамка, виньетка — подпроект 5.
- UI-панель выбора палитры и слайдеров — подпроект 6. Здесь параметры существуют только как поля `WorldMapRenderer`/конфига, без UI.
- Туман войны — в roadmap, не в этой инициативе.
- Полная переклассификация биома по алгоритму прототипа — не делаем, используем существующий `BiomeClassifier`.

## Архитектура рендера

### Было
Один меш: веер треугольников на клетку, цвет — vertex color per-vertex, все вершины одной клетки одного цвета (`WorldMapRenderer.BuildMesh`/`GetColorForCell`/`RecolorOnly`). Материал — кастомный unlit-шейдер `WorldGen/VertexColorUnlit`, читающий только vertex color. Клик по карте: `MeshCollider.Raycast` → `hit.triangleIndex` → `triangleToCellId[]` → `VoronoiCell`.

### Стало
Один плоский квад размером `mapWidth × mapHeight` в плоскости XZ (4 вершины, UV 0..1) вместо тысяч клеточных вееров. Цвет приходит из `Texture2D`, запечённой на CPU по всем клеткам разом (`MapRasterizer.Bake`). Материал — стандартный встроенный шейдер `Unlit/Texture` (собственный шейдер `VertexColorUnlit.shader` для этого пути больше не нужен, его файл не удаляем — им ещё может пользоваться debug-режим, если понадобится, но по умолчанию отключаем от него материал). `Texture2D`: `TextureFormat.RGBA32`, `filterMode = Bilinear`, `wrapMode = Clamp`.

Отдельно, той же ширины/высоты в пикселях, запекается **несмешанный `cellId`-буфер** (`int[]`, один вызов `MapRasterizer.Bake` возвращает оба массива разом) — используется ТОЛЬКО для хит-тестинга, никогда для отображения.

Взаимодействие: `MeshCollider.Raycast` на квад → `RaycastHit.textureCoord` (Unity считает это из UV меша через барицентрические координаты автоматически, для квада тривиально) → перевод в пиксельные координаты → `cellId[y*width+x]` → `cellById[id]`. `TryGetSiteHitPoint` не меняется (работает через `InverseTransformPoint`, не зависит от структуры меша).

**Существующие оверлеи не трогаем**, они уже независимы от способа заливки базового меша:
- `MapBorderBuilder`-риббоны границ регионов (`showRegionBordersLayer`) — отдельная геометрия по рёбрам клеток, продолжает работать как есть, во всех режимах.
- Риббон берега (`showCoastlineLayer`) — в режимах Height/Region/Biome и в Combined без сглаживания продолжает работать как есть. В Combined со сглаживанием (см. ниже) новый растр уже рисует собственное свечение берега — риббон в этом случае скрывается, чтобы не дублировать эффект.
- Реки (`BuildRivers`, `LineRenderer`) — не меняются, по-прежнему за флагом `enableRivers` (не трогаем в этом подпроекте).

### Режимы отображения — одна унификация вместо четырёх путей
`MapRasterizer.Bake(cells, displayMode, config)` обслуживает все существующие режимы одним пикельным циклом:
- **Height / Region / Biome, и Combined при `smoothBorders = false`**: для каждого пикселя берём только ближайшую клетку (без блендинга) и вызываем существующую логику `GetColorForCell`/`RegionColorPalette` один в один — визуально идентично сегодняшнему результату, только через текстуру вместо вершин.
- **Combined при `smoothBorders = true` (новое поведение, включено по умолчанию)**: включается полный «нарисованный» конвейер на `MapPalette` (сглаживание, рельеф, вариации, зерно, свечение берега, глубина воды) — описан ниже.

`RegionColorPalette.cs` не меняется и не удаляется — обслуживает первую ветку. `MapPalette.cs` — новый файл, только для второй ветки.

## Поиск ближайшей клетки (`NearestCellLookup`)

Диаграмма Вороного по определению — это "клетка = множество точек, ближайших к данному Site", поэтому point-in-polygon не нужен: для пикселя ищем ближайший `Site` среди клеток. Структура: grid-bucket по позиции `Site` с размером ячейки `≈ minPointDistance` (уже существующий параметр генерации, определяющий типичное расстояние между сайтами) — поиск ближайшего сайта расширяющимся кольцом бакетов вокруг точки, амортизированно O(1) при равномерном распределении точек (у нас так и есть после Lloyd-релаксации).

Публичный API:
- `VoronoiCell FindNearest(Vector2 point)` — для `cellId`-буфера и для «hard» (несглаженного) сэмплинга.
- `IEnumerable<(VoronoiCell cell, float distance)> FindWithinRadius(Vector2 point, float radius)` — для сглаженного блендинга (см. ниже).

Самотест (фикстура из 5–6 клеток с известными позициями сайтов, проверка что `FindNearest` возвращает геометрически верную клетку в нескольких контрольных точках, включая точку точно на границе двух клеток).

## Конвейер запекания (`MapRasterizer.Bake`)

Разрешение текстуры: `rasterLongSide` (новое поле `WorldMapRenderer`, по умолчанию `2048`), меньшая сторона — по аспекту `mapWidth:mapHeight`. Запекание — один проход по всем пикселям; интегрируется как дополнительный шаг в уже существующий поэтапный конвейер генерации (`WorldGenerator.GenerateWorldStepped` + `GenerationProgressUI`), чтобы у пользователя был прогресс-бар, а не подвисание интерфейса.

Для каждого пикселя `(x, y)` → мировая точка `(px, pz)`:

1. **Сэмплинг полей.** Через `NearestCellLookup` получаем ближайшую клетку (для `cellId`-буфера и для «hard»-режима) и, если `smoothBorders`, список клеток в радиусе `smoothRadius = minPointDistance * 1.5` (новое поле, дефолт как формула). Для каждой из них — `EffectiveElevation`, `BiomeFamily` (см. маппинг ниже), `EffectiveTemperature`, `waterDepth01` (переиспользуем существующую механику `GetWaterDepth01`/`oceanDistanceFromLand`, посчитанную один раз на клетку до растеризации — НЕ пересчитываем per-pixel distance transform), `EffectiveIsOcean`/`EffectiveIsLake`.

2. **Категория пикселя (суша/океан/озеро) — всегда «hard».** Определяется `EffectiveIsOcean`/`EffectiveIsLake` БЛИЖАЙШЕЙ клетки, независимо от `smoothBorders`. Между категориями блендинга нет никогда — граница берега всегда идёт точно по истинной границе Вороного; смягчает её на глаз только «свечение берега» (шаг 7), не подмешивая цвет воды в сушу или наоборот.

3. **Блендинг внутри категории (только суша, только когда `smoothBorders=true`).** Среди соседей в радиусе `smoothRadius`, отбрасывая водные клетки, вес каждой `w = 1 / (distance² + ε)`, нормализуем по сумме. Блендим **непрерывные** величины (elevation, temperature) и **базовый цвет биом-семейства** (не индекс биома — блендинг индексов бессмысленен) взвешенной суммой. Результат — органичные, а не полигональные переходы между сухопутными биомами; при `smoothBorders=false` — просто значения ближайшей клетки (сегодняшний вид, но через текстуру). Вода блендингу не подлежит вообще — её цвет определяется только `waterDepth01` ближайшей водной клетки (шаг 4).

4. **Базовый цвет.** Суша: `base = MapPalette.GetSlotColor(activeTheme, biomeFamily)` (уже блендированный на шаге 3). Океан: `Color.Lerp(shallow, abyss, waterDepth01)`. Озеро: `Color.Lerp(lakeS, lakeD, waterDepth01)`.

5. **Региональная тонировка (только суша).** Блендим `base` к `Lerp(tintCool, tintWarm, InverseLerp(0.28, 0.70, temperature))` фиксированным весом `0.38` (не зависит от `regionVariation` — это ровно то поведение референса); затем добавляем микро-шум (`Noise.fbm(nx*1.6+20, ny*1.6+40, seed+1500, 2)`, см. ниже) к RGB с амплитудой `38 * (regionVariation/100)` (r полным весом, g×0.9, b×0.7 — сохраняет тёплый/холодный цветовой сдвиг по каналам, как в референсе).

6. **Рельеф (hillshade, только суша).** Вода этот шаг не проходит — в референсе рельефное затенение применяется только к земле (вода получает собственный, отдельный трактат в шаге 4/7/9, без hillshade). Градиент elevation по соседним пикселям (Sobel/центральная разность по X/Z — на текстуре это естественнее и глаже, чем сегодняшнее усреднение по `NeighborIds`). Переиспользуем существующую `RegionColorPalette.HillshadeBrightness(gradX, gradZ, reliefStrength, reliefLightAzimuth, reliefAmbient)` без изменений — она уже самотестирована. Дополнительно — «холодный лунный» подсвет на освещённых склонах: добавляем `palette.light * ndotl * coldAmt`, где `coldAmt = 0.10 + (coldLight/100) * 0.30`; `ndotl` — тот же скалярный продукт, что уже вычисляется внутри `HillshadeBrightness` (потребуется небольшое расширение сигнатуры/дополнительный метод, возвращающий сырой `ndotl`, а не только финальную яркость — деталь для этапа плана).

7. **Граница берега — с обеих сторон.** Со стороны воды: водные пиксели в пределах нескольких текселей от суши блендятся к `palette.glow` весом `0.32 + coldAmt*0.5` (мягкое свечение). Со стороны суши: сухопутные пиксели, соседствующие с водой, получают тонкую обводку `palette.outline` (реплика прототипного жёсткого «coastline»-штриха поверх мягкого водного свечения — именно это сочетание даёт вид «нарисованного тушью» берега).

8. **Зерно (только суша).** Малый шум `(valueNoise(x*0.5, y*0.5, seed+61) - 0.5) * 7` добавляется к RGB сухопутных пикселей. Вода вместо этого получает **рябь** — независимый шум `(fbm(x/40, y/26, seed+401, 2) - 0.5) * 10`, чтобы вода и суша не казались зашумлёнными синхронно одним и тем же паттерном.

9. **Дополнительная лайтнесс-вариация (только суша).** Отдельный, более крупномасштабный проход шума поверх всего предыдущего: умножаем RGB на `1 + rgB * (0.24) * (regionVariation/100)`, где `rgB = Noise.fbm(nx*2.0+50, ny*2.0+70, seed+1600, 2) - 0.5`. Даёт крупную «рванность» тона на уровне всей карты, отдельно от локального зерна шага 8 и локальной тонировки шага 5 (три разных масштаба шума — согласно референсу).

10. **Виньетка и общее затемнение (`darkness`).** Радиальное затемнение от центра текстуры к краям (суша и вода одинаково), сила = `darkness/100`; применяется отдельным дешёвым финальным проходом поверх уже готового результата шагов 1–9. При смене только `darkness` (без смены прочих параметров) достаточно повторно применить только эту маску к уже запечённому результату, не пересчитывая всё заново — см. `ReapplyDarkness()` в разделе «Взаимодействие и производительность кисти» ниже.

`BiomeFamily` — новый enum в `MapPalette.cs`: `Sea, Lake, Coast, Snow, Tundra, Highland, Badlands, Forest, ForestWarm, Moor, Plains`.

## Взаимодействие и производительность кисти

`RebakeAll()` — полный перезапек всей текстуры (смена режима, палитры, смены большинства клеток разом — `ApplyClimateOverride`/`ApplyBiomeOverride` и т.п. на множестве клеток). Вызывается там, где сегодня вызывается `RecolorOnly()`.

`RebakeRegion(IEnumerable<VoronoiCell> touchedCells)` — новый метод, используемый кистью (`BrushAdjustElevation/Temperature/Moisture`, `BrushSetBiome`): считает bounding rect затронутых клеток (в мировых координатах через их `Polygon`), расширяет его на `smoothRadius` (чтобы захватить область, куда блендинг «протекает» из соседних непосредственно не тронутых клеток), переводит в пиксельные координаты текстуры, перезапекает только этот под-прямоугольник (`Texture2D.SetPixels32` на суб-области + `Apply(false)`), не трогая остальную текстуру. Это меняет сегодняшнее поведение «весь меш перекрашивается на каждое движение кисти» на «только затронутая область» — попутно закрывает пункт roadmap про производительность кисти.

`cellId`-буфер перезапекается тем же вызовом, т.к. `WaterOverride`/`BiomeOverride` не меняют геометрию Вороного, только сами клетки — переприсваивание пикселей клеткам не требуется, только их сэмплированные значения.

`ReapplyDarkness()` — отдельный, самый дешёвый путь: когда меняется только `darkness` (слайдер виньетки/затемнения, подпроект 6), полный `RebakeAll()` не нужен — достаточно заново применить финальный проход шага 10 поверх уже готовых (шаги 1–9) пикселей текстуры и вызвать `Apply()`.

## Тестирование

Все ключевые шаги — чистые C#-функции, самотестируемые через `[ContextMenu]` (стиль, уже принятый в проекте):
- `Noise.cs` — `hash`/`valueNoise`/`fbm`, самотест на детерминированность (один и тот же `(x,y,seed)` даёт одно и то же значение) и на диапазон `[0,1]`.
- `NearestCellLookup` — фикстура из нескольких клеток, проверка корректности `FindNearest` в контрольных точках, включая границу двух клеток.
- `MapPalette.GetFamily` — таблица `Biome → BiomeFamily`, самотест проверяет все 16 значений `Biome` явно (защита от будущего добавления биома без записи в таблицу).
- `MapRasterizer` — инвариантный самотест: элевация, сэмплированная в пикселе, ближайшем к `cell.Site`, совпадает с `cell.EffectiveElevation` (регрессия на связку lookup+сэмплинг); также самотест «hard-режим (smoothBorders=false) даёт тот же цвет, что сегодняшний `GetColorForCell` для той же клетки» — гарантия визуальной паритетности старых режимов.

## Риски и открытые вопросы

- **Производительность запека.** Полный проход по ~2048×~1300 пикселям (при дефолтном аспекте) с несколькими `fbm`-вызовами на пиксель на чистом C# без Job System/Burst может занимать заметное время (по аналогии с текущей генерацией — секунды, не миллисекунды). Смягчение: запек — часть уже существующего поэтапного конвейера генерации с прогресс-баром, не блокирующий UI фриз. Если после реализации окажется медленно — `Parallel.For` по строкам текстуры без добавления Job/Burst как первый шаг оптимизации (не делаем заранее, YAGNI).
- **`PolygonTriangulator.cs` становится мёртвым кодом** для основного рендер-пути (не используется новым `BuildMesh`). Не удаляем в этом подпроекте — самотесты `WorldMapRenderer` (`SelfTestBorderClassification` и др.) фикстурируют `Polygon`/`NeighborIds` независимо от рендера, так что явной привязки нет; окончательное решение об удалении — по итогам финального ревью ветки.
- **`ndotl` из `HillshadeBrightness`.** Текущая сигнатура возвращает только финальную яркость; шаг 6 (рельеф — холодный лунный подсвет) нуждается в сыром `N·L` отдельно. Точное решение (перегрузка/доп. метод) — на этапе плана, не блокирует дизайн.
- **Видимость координационного риска между `smoothRadius` и производительностью `NearestCellLookup.FindWithinRadius`** — при плотной сетке клеток и большом `smoothRadius` число соседей на пиксель растёт; дефолт (`minPointDistance*1.5`) выбран консервативно, финальную калибровку делает реализация по результату визуальной проверки.
